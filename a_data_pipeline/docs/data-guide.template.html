每个字段从哪里来，清洗怎样决定保留

共同处理规则集中在 。它把一行原始 JSON 转成规范记录，并给出 valid、invalid、parse_error 或 blank 状态。

@@CLEANING_GRAPH@@

① 无法解析的原始行

UTF-8 或 JSON 失败 → parse_error。保存原始行、来源和原因；不进入有效事件。无效 UTF-8 还保留十六进制字节。

② 关键字段不合法

JSON 根不是对象，或事件 ID、仓库 ID、类型、时间无效 → invalid。ID 需为可用的正整数（不接受布尔值/浮点）；时间需带时区。保存排除原因。

③ 可选字段缺失或时间偏离

仓库名称、actor ID/login 无效时置空并写问题列表；时间与档案小时不一致时标记。记录仍可进入有效集合，随后照常去重。

④ 相同事件 ID、相同完整内容

先把完整 JSON 的键排序后计算哈希（包含 payload）。同一 ID 只有一个内容版本时，保留最早来源小时的最小行号；其他出现写入重复文件。空格或键顺序差异不会制造新内容版本。

⑤ 相同事件 ID、不同完整内容

同一 ID 对应多个完整内容版本时，暂排除该 ID 的全部有效出现，并保留冲突记录供复核。此处按有效记录比较，关键字段无效的行已另存。

⑥ 空行与本轮保留项

空行计数后跳过。未知事件类型和机器人活动保留；没有对 actor 追加“人工开发者”筛选，也没有建立 AI 标签。

Python 将解析/字段无效行写到 rejected_records.jsonl；可选问题写到 flagged_records.jsonl；重复与冲突分别另存。Spark 保存对应结果为 JSON 分片目录。

这张表用什么规则计算？
SELECT repo_id, event_date, event_type, COUNT(*) AS event_count
FROM cleaned_events
GROUP BY repo_id, event_date, event_type;

Python 在 SQLite 中执行这组逻辑；Spark 用 DataFrame 的 groupBy(...).count() 得到对应结果。@@GROUP_N@@ 是分组的行数，所有分组的计数之和仍是 @@EVENT_N@@ 条事件。

按日期分组，当前仍只覆盖一个小时

文件名中的 daily 说明分组粒度；当前数字来自实际读取的小时档案。要得出完整日/月计数，需要补足相应档案并核实覆盖。表只包含出现过的分组，没有自动为未读取时段或没有观察到的组合填零。

同样的数据在 CSV、Parquet 和 SQLite 中看起来为什么不同？

CSV 是带表头的文本：空值显示为空格位，问题列表保存为 [] 一类 JSON 文本。.csv.gz 再把这个 CSV 压缩。Parquet 保存明确类型，例如 int64、UTC 微秒时间、日期、布尔和列表。SQLite 中时间是规范字符串、问题列表是 JSON 文本、布尔标记保存为 0/1；同一字段的含义保持一致。

events_clean.parquet/ 和 Spark 的 *.jsonl/ 是目录。里面的 part-* 文件共同组成一张表，_SUCCESS 和 .crc 是写入标记/校验文件。读取整张表时指向目录；这些辅助文件不作为额外事件。

05

为什么还有 Spark 版本，核对了哪些东西

python/ 与 spark/ 由两种计算方法生成，业务规则共享，去重和分组分别实现。它们是同一份样本的复算结果。后续分析选一套使用；拼接两套会重复计入同样事件。

Python 路径

逐行解析 → SQLite 保存有效事件 → SQL 去重/冲突分组 → 导出 CSV 与 PyArrow Parquet。

用于解释规则、保留过程记录和形成参考结果。

Spark 路径

小时档案分配给分区 → 同一逐行解析器 → 明确 schema 的 DataFrame → 窗口去重与分组 → Spark Parquet。

用于确认 Spark 实现正确，为后续并行度实验准备任务。

本次 local[2] 在一台机器上使用 2 个 worker 线程；1 个小时文件只对应 1 个读取任务。多个小时文件才能有跨文件读取并行，后续 DataFrame 分组也有自己的 shuffle 分区。单个 gzip 文件没有被切成多份输入。

事件 Parquet 统一用 UTC 微秒时间。Spark 显式设置 spark.sql.parquet.outputTimestampType=TIMESTAMP_MICROS，并读回检查，供组员直接用同一类型处理。对应的官方格式说明。

展开本次全部自动核对项@@COMPARE@@
当前的验证范围

脚本比较输入哈希/范围/规则版本、清洗质量计数、事件 ID 与所有事件字段、CSV 日分组，并读回事件 Parquet 验证值与类型。候选仓库表、名称历史表和日计数 Parquet 尚未在比较脚本中逐字段自动对比。

各阶段耗时包含导出、审计和核对工作；D 的正式性能实验需另固定计算任务、计时边界和并行配置，当前运行不直接给出加速结论。

哪些文件算原始输入？

为什么清洗前后数量相同？

本次 @@RAW_N@@ 条记录都通过关键字段校验，且没有重复/冲突。因此数量相同；嵌套信息已整理成共同字段并新增来源与问题标记。其他档案仍需按同样规则检查。

能否用 repo_daily_counts 当作完整一天的活动？

当前只读取一个小时。按日期分组说明存储粒度，覆盖范围仍由输入清单决定。完整日/月分析要先收集所需档案并评估覆盖。

是否已经得到了 AI 仓库的生命周期结论？

当前完成的是基础管道与正确性验证。AI 标签、仓库创建时间、长观察期和分析口径都需补齐后再形成研究结论。
