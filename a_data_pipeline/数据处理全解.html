先区分“执行顺序”和“数据依赖”

一条命令按顺序执行各阶段；但检查、Python 清洗、Spark 清洗会分别读取同一份原始档案。预览和检查报告是给人看的记录，清洗脚本会重新读取完整原始文件。

执行顺序获取 / 校验→检查→Python 清洗→Spark 清洗→结果核对
当前样本的边界

读取的是一个小时档案，包含各种仓库的公开事件。AI 标签、仓库创建时间和首年观察数据属于后续工作。文件完整可读说明档案读取成功；GitHub 活动捕获是否完整仍需后续覆盖与质量研究。

01

原始数据是什么结构

当前实际读取 1 个小时档案，其中一个原始输入是 data/raw/2024-01-15-0.json.gz。.gz 是压缩形式；脚本边解压边逐行读取，没有另存一份完整解压文件。

解压后有 197,313 个非空行；每一行是一个独立 JSON 对象。一个仓库在这一小时发生多次活动，会重复出现在不同事件行里。GH Archive 官方说明提供按 UTC 小时获取事件档案的方式。

一次事件与具体工作量要分别定义

第一条 PushEvent 的 payload.commits 实际有 15 个 commit，size=15、distinct_size=1。本轮按事件计数，它贡献 1 条 PushEvent。PR 的 payload.action 可以描述不同操作；加星详情与推送详情的结构也不同。要分析 commit、PR 操作或合并数，后续需再展开详情并定义指标。

以下解释本文真实示例中出现的结构。共同事件表提取固定字段；这些详情对象仍完整保存在原始档案，可按研究问题再展开。

原始路径怎样理解本轮处理去向
actor.id / actor.login发起者 ID 与账号名；一个 actor 可触发多次事件。进入 actor_id / actor_login。
actor.display_login账号的显示形式，可能与 login 的大小写或展示形式不同。留在原始档案。
actor.gravatar_id / actor.avatar_url头像相关标识与地址，属于账号详情。留在原始档案。
actor.url获取该账号对象的 API 地址。留在原始档案；本轮不据此请求用户 API。
repo.id / repo.name仓库 ID 与 owner/repo 名称；与事件 ID 分属不同对象。进入 repo_id / repo_name。
repo.url仓库对象的 API 地址；原始共同对象本身未给本轮需要的创建时间与 AI 标签。留在原始档案；B 后续补仓库元数据。
org.*组织的 ID、账号和相关地址等信息；此示例提供所属组织对象。留在原始档案。
PushEvent.payload.repository_id / push_id推送详情中的仓库标识和推送标识。事件主键仍使用顶层 id。留在 payload。
PushEvent.payload.size / distinct_size历史推送 payload 的提交计数字段，本例分别为 15 和 1；本轮事件计数使用记录条数。留在 payload，后续 commit 指标需单独定义。
PushEvent.payload.ref / before / head推送目标 Git 引用及前后位置的提交哈希，可进一步研究分支与代码活动。留在 payload。
PushEvent.payload.commits[]提交对象数组；本例 15 项。对象中有 sha、author、message、distinct、url 等字段。完整数组在原档案；页面预览只显示第一项。
PullRequestEvent.payload.action / number / pull_requestPR 的操作类型、仓库内编号和 PR 详情对象。14 条 PR 事件表示 14 次观察到的 PR 活动，具体操作要看 action。本轮保留类型计数；动作、状态、标题、分支等详情留在 payload。
WatchEvent.payload.action本文真实记录是 started，对应加星活动；当前只计观察到的事件。本轮保留 WatchEvent 计数；它不提供仓库某时刻的累计星数。

原始对象中可能还有类型专属字段。查看具体例子的 JSON 可定位它们；最终共同表没有把 payload 内的所有属性混成一套列。读取完整详情时，可用来源文件与行号找到同一事件。

字段含义参考 GitHub 事件类型文档；这里展示的具体字段和值以下载到的 2024 历史记录为准，历史 payload 与当前 API 文档可能有差异。

共同处理规则集中在 。它把一行原始 JSON 转成规范记录，并给出 valid、invalid、parse_error 或 blank 状态。

记录怎样流向不同文件

① 无法解析的原始行

UTF-8 或 JSON 失败 → parse_error。保存原始行、来源和原因；不进入有效事件。无效 UTF-8 还保留十六进制字节。

② 关键字段不合法

JSON 根不是对象，或事件 ID、仓库 ID、类型、时间无效 → invalid。ID 需为可用的正整数（不接受布尔值/浮点）；时间需带时区。保存排除原因。

③ 可选字段缺失或时间偏离

仓库名称、actor ID/login 无效时置空并写问题列表；时间与档案小时不一致时标记。记录仍可进入有效集合，随后照常去重。

④ 相同事件 ID、相同完整内容

先把完整 JSON 的键排序后计算哈希（包含 payload）。同一 ID 只有一个内容版本时，保留最早来源小时的最小行号；其他出现写入重复文件。空格或键顺序差异不会制造新内容版本。

⑤ 相同事件 ID、不同完整内容

同一 ID 对应多个完整内容版本时，暂排除该 ID 的全部有效出现，并保留冲突记录供复核。此处按有效记录比较，关键字段无效的行已另存。

⑥ 空行与本轮保留项

空行计数后跳过。未知事件类型和机器人活动保留；没有对 actor 追加“人工开发者”筛选，也没有建立 AI 标签。

Python 将解析/字段无效行写到 rejected_records.jsonl；可选问题写到 flagged_records.jsonl；重复与冲突分别另存。Spark 保存对应结果为 JSON 分片目录。

同样的数据在 CSV、Parquet 和 SQLite 中看起来为什么不同？

CSV 是带表头的文本：空值显示为空格位，问题列表保存为 [] 一类 JSON 文本。.csv.gz 再把这个 CSV 压缩。Parquet 保存明确类型，例如 int64、UTC 微秒时间、日期、布尔和列表。SQLite 中时间是规范字符串、问题列表是 JSON 文本、布尔标记保存为 0/1；同一字段的含义保持一致。

events_clean.parquet/ 和 Spark 的 *.jsonl/ 是目录。里面的 part-* 文件共同组成一张表，_SUCCESS 和 .crc 是写入标记/校验文件。读取整张表时指向目录；这些辅助文件不作为额外事件。

为什么还有 Spark 版本，核对了哪些东西

python/ 与 spark/ 由两种计算方法生成，业务规则共享，去重和分组分别实现。它们是同一份样本的复算结果。后续分析选一套使用；拼接两套会重复计入同样事件。

Python 路径

逐行解析 → SQLite 保存有效事件 → SQL 去重/冲突分组 → 导出 CSV 与 PyArrow Parquet。

用于解释规则、保留过程记录和形成参考结果。

Spark 路径

小时档案分配给分区 → 同一逐行解析器 → 明确 schema 的 DataFrame → 窗口去重与分组 → Spark Parquet。

用于确认 Spark 实现正确，为后续并行度实验准备任务。

本次 local[2] 在一台机器上使用 2 个 worker 线程；1 个小时文件只对应 1 个读取任务。多个小时文件才能有跨文件读取并行，后续 DataFrame 分组也有自己的 shuffle 分区。单个 gzip 文件没有被切成多份输入。

事件 Parquet 统一用 UTC 微秒时间。Spark 显式设置 spark.sql.parquet.outputTimestampType=TIMESTAMP_MICROS，并读回检查，供组员直接用同一类型处理。对应的官方格式说明。

读完后应该能回答的几个问题

哪些文件算原始输入？

data/raw/*.json.gz 是从 GH Archive 取得的原始档案。检查预览、清洗表、SQLite、所有 JSON 报告都由脚本生成；它们的类别和来源在文件表中标明。

为什么清洗前后数量相同？

本次 197,313 条记录都通过关键字段校验，且没有重复/冲突。因此数量相同；嵌套信息已整理成共同字段并新增来源与问题标记。其他档案仍需按同样规则检查。

能否用 repo_daily_counts 当作完整一天的活动？

当前只读取一个小时。按日期分组说明存储粒度，覆盖范围仍由输入清单决定。完整日/月分析要先收集所需档案并评估覆盖。

是否已经得到了 AI 仓库的生命周期结论？

当前完成的是基础管道与正确性验证。AI 标签、仓库创建时间、长观察期和分析口径都需补齐后再形成研究结论。

遇到无法解释的计数，应该查哪里？

先看 quality_summary.json 与 hourly_quality.csv，再看对应异常/重复/冲突文件和 SQLite。使用事件表中的 source_file + source_line 可定位原始档案的那一行，回查完整 payload。
