## 真实失败与必要修复

第一轮运行在两个 Spark 分片输出后、批次验收阶段退出 1。错误为 Spark 正常移除 `_temporary/...` 子目录时，后台容量采样的 `Path.rglob()` 遍历遇到目录消失。采样线程把该 FileNotFoundError 记为 stop_reason，主线程随后拒绝验收。旧采样代码虽然捕获了文件 stat 的消失，却没有捕获目录枚举本身的消失。

修复位于 `a_data_pipeline/rolling_pipeline/batch_support.py::tree_bytes()`：改为迭代 `os.scandir()`；在目录枚举与单个条目查询两处，仅容忍 FileNotFoundError。PermissionError 及其他 I/O 错误继续传播。产物 inventory、哈希复验、内容验收与容量阈值未放宽，清洗和全局去重规则未改。

新增两项回归：发现目录后、扫描前真实移除本次新建空目录，采样仍正确计入保留文件；权限异常必须继续失败。本地两项专项通过，修复版在 VM 上 **21 项 Linux 回归全部通过**（20.825 秒测试内部计时），包括原窗口不变性和已知冲突答案。Spark 桥接及双主机日志单元测试依然是 fixture；本报告的真实 Spark 证据来自随后完成的五个应用。

原失败尝试完整保留，没有更改其 accepted 状态或手工补标成功。修复改变代码身份，因此新建 release 和输出重跑，复用原已校验输入；这不是同一身份续跑，不计为任务四的受控恢复验收。

原失败运行：`/data/cs5488/runs/rolling_v1_20261113_task2_7h_l4_6h/`，退出 1、外层耗时 358.998 秒，保留约 1.24 GB；其原始峰值与 stop_reason 在 JSON 中单独保留，不并入成功计时。

此外，最初使用 urllib 默认请求头的代理 HEAD 诊断曾返回 403。使用现有生产下载器原有请求头后，七档 HEAD 均返回 200，实际 GET 和输入哈希也通过；403 的具体原因未确定，没有为此修改生产请求头、Clash、路由或 SSH 配置。
