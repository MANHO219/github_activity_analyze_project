# 任务 2–5 原始要求解释与验收范围修正

2026-11-12。以用户本轮重新给出的原始要求为当前需求基准。此前“三种窗口各跑完整两天、另存完整 Python 结果和三个比较库、全部同时保留”是较重的验收及存储方案，现不再作为原需求的硬性标准。既有运行、失败记录、源包和原始计时保留，不改写历史测量。

## 需求与验收方案分开

| 任务 | 原始要求 | 不应额外固化的条件 |
|---|---|---|
| 2：统一批处理入口 | UTC 起止范围 `[start,end)`；范围与批次窗口独立；默认 24h、支持如 6/12/24h；路径参数化；可选择 L1/L4/D4；正确处理跨日/月和尾批；依赖与 Worker 路径可访问性有说明 | 不要求为每一种可选窗口都生成完整两天副本；不把完整两天所有验收都归为任务二入口实现本身 |
| 3：共用 Spark 逻辑 | 三配置调用同一套读取、解析、字段校验、局部去重/冲突、日汇总与输出；月级适配先默认 L4 | 不要求重做三配置×三窗口×三次性能实验，不改 VM vCPU 来验证 local[1] |
| 4：滚动验收与续跑 | 每批下载校验、处理、核对、保存清单/质量/全部有效出现索引、验收与按清单清理；失败保留、输入复用、已验收结果复验后跳过；最终跨批裁决并重算统计 | 不把 retained SQLite、完整事件 CSV、每个比较数据库都自动列为必须永久保存的最终交付；也不能为省空间丢失有效出现证据或降低复验能力 |
| 5：阶段计时与汇总 | 各阶段墙钟时间、输入规模、事件量、版本、配置与计时边界；已有六小时实验作为本轮性能结果，短区间验证新流程功能 | 不重新做两天性能基准，不用缓存复用时间当作首次处理，不累计父子计时 |

连续两天是滚动适配的综合功能验收范围，覆盖不同分批、失败续跑、清理及最终一致性；它横跨任务 2–5。支持多个窗口是产品能力，不等于必须把每个例子都做成一套完整两天实验。

## 修订后的验收设计

以下是满足原需求的精简设计建议，不是原文新增的硬性要求；本轮只修正文档，没有开始执行此新设计。

1. 沿用已选的连续两天来源 `[2024-01-15T00:00Z,2024-01-17T00:00Z)`，固定来源档案及 SHA-256。选定一个主窗口完成正常滚动，例如默认 24h。
2. 用另一种分批方式验证同一来源范围的最终一致性，例如 6h 对 24h。这里推荐两种窗口是具体方案选择；原文没有指定必须采用哪两个或必须同时保留所有过程文件。12h 能力可由短区间真实样本及已有合成边界测试补充验证，不再默认第三次完整两天运行。
3. 对跨日、跨月、非整批尾段、批内及跨批重复/冲突使用有预先确定答案的样本；真实两天若没有出现冲突，不能据此宣称相关边界已被真实数据覆盖。保留已有“全部有效出现”规则，不仅比较局部保留事件。
4. 与 Python 参照核对相同输入覆盖的完整事件字段/类型、重复次数、日统计、候选表、覆盖与重复/冲突证据。可复用经输入和规则身份核验的既有参照；如需新建，可研究分阶段生成/核对及过程存储策略，不把“另存一整套永久过程库”当作需求。不能只拿旧日汇总 CSV 代替明细对账，也不能把局部比较当作全局最终裁决验证。
5. 续跑、损坏拒绝、互斥、最终合并恢复和清理仍需真实验收，不因精简窗口数量而取消。三配置先用相同短样本验证；D4 的两台不同 Worker 必须有真实成功 TaskEnd。
6. 最终交付清洗事件 Parquet、日活动表、候选表、覆盖清单、质量摘要，并保留全部有效出现的去重证据及复验/续跑必需的清单、身份、质量和失败记录。日活动表继续为 `repo_id,event_date,event_type,event_count`。

现有实现把多个 SQLite、事件 CSV 和比较表全部落盘并登记进验收 inventory，因此仅从需求中去掉额外副本，并不会自动降低当前实现的占用。任何面向未来运行的精简，都要先调整并验证验收清单、复验、续跑和全局裁决，再重新测量，不能直接删除文件来满足预算。

## 容量结论修正

- 原真实 1h 测量仍有效：L4 与 Python 各 212,804 条事件，19 项完整比较通过；原始输入、运行及比较库占用不修改。
- 原 128–136 GiB 是“三份完整两天 Spark + 完整 Python + 三份完整比较库及原实现保留策略”的外推，不是原始功能需求本身的最低容量。
- “至少 200 GiB 可用”和“Master 扩至 250 GB”是针对旧重型方案的余量建议，现撤销其作为任务继续前置条件的地位；没有实施扩容。
- 也不能反向承诺现有 31.88 GiB 一定够。修订后尚无有效容量预算，应先明确窗口样本矩阵和未来过程存储策略，再按实测重新计算。既有 raw、SQLite、Parquet、索引、失败目录和历史证据全部保留。
- 不应仅凭旧方案超出容量就把“先扩盘”当作唯一下一步。先审视非交付必需的重复落盘；若精简后仍不足，再报告具体缺口和可选存储方案。
